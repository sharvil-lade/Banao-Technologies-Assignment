# Validation — how we know it works

The assignment asks: *"How do you know your tool's output is correct, and how
often is it not?"* Four independent layers, because each catches what the others
cannot. A total can reconcile perfectly and still be built from wrong rows.

Every figure here is regenerated by `python -m vireo.pipeline` and locked by a
test in `tests/`. None of it is typed in by hand.

---

## Layer 1 — Deterministic reconciliation

**The client's own test.** Arjun Mehta, 9 Sep: *"I want the total to reconcile."*

| Step | Adjustment | Running total |
|---|---:|---:|
| Raw export summed as exported | | ₹23,01,24,081 |
| Legacy paise → rupees | −₹22,30,53,138 | ₹70,70,943 |
| Migration duplicates removed | −₹3,61,011 | ₹67,09,932 |
| Canonical total | | **₹67,09,932** |

**Residual ₹0.00.** The pipeline refuses to publish if it is not.

Six aggregation identities, all **PASS**:

```
sum(monthly)     == sum(by reason) == sum(by agent) == canonical total
count(monthly)   == count(by reason) == count(by agent) == canonical rows
```

These catch the classic silent under-report: a `groupby` dropping rows on a null
key. If any one fails the run aborts.

### Self-proving conversion factor
The ÷100 is not trusted from config. `verify_legacy_conversion()` re-derives it
from the duplicate pairs on every run and **aborts if it stops matching**:
125 pairs, ratio 100.0, std dev 0.0, and 775/775 legacy amounts divisible by 100.

The strongest evidence arrived *after* the fix: once converted, **125 of 125**
duplicate pairs agree to the rupee across both source systems, **0 disagree**.
Two independent systems recording the same refund now produce the same number.

## Layer 2 — Independent recomputation

Reconciliation checks the pipeline against itself. This layer checks it against
a **second implementation**.

`vireo/validate_sample.py` imports **none** of the transformation code. It reads
`tickets.csv` with the stdlib `csv` module and re-derives every field with its
own logic, then compares.

### Headline totals

| Check | Independent | Pipeline | Difference | Result |
|---|---:|---:|---:|---|
| Canonical refund total | ₹67,09,932 | ₹67,09,932 | ₹0 | **PASS** |
| Canonical refund count | 2,340 | 2,340 | 0 | **PASS** |

### Record sample

| | |
|---|---|
| Sample size | **60 canonical refund records** |
| Selection | random, `seed=20260921` — reproducible, so any reader can re-check the same 60 |
| Checks per record | **15** |
| **Total field checks** | **900** |
| Records fully correct | **60 of 60** |
| **Record error rate** | **0.00%** |
| **Field error rate** | **0.000%** |

The 15 checks per record: exists in raw · duplicate status · source system
chosen · amount · raw amount preserved · conversion factor · month · reason code
unchanged · agent id · agent name · agent team · replacement flag · goodwill-cap
flag · open-ticket flag · AI did not alter a fact.

**What this does and does not prove.** It proves the pipeline implements the
decisions in `decisions.md` faithfully, on a reproducible sample, verified by
code that shares no logic with it. It does **not** prove the decisions
themselves are right — that is what the decision log and the reconciliation
against the client's own ₹11 lakh figure are for.

## Layer 3 — Edge-case tests

**71 tests, all passing** (`python -m pytest tests/ -q`).

| Edge case | Tests | What is asserted |
|---|---|---|
| Legacy vs current money | `test_normalise.py` | ÷100 on legacy only; keyed on `source_system`, never on magnitude, so a genuine ₹13,998 refund is not mistaken for paise |
| Duplicates | `test_dedupe.py` | Helpdesk row wins; the twin is retained in the audit; **₹90,000 never reaches output**; a test demonstrates that naive `drop_duplicates()` *would* have banked the paise value |
| Conflicting duplicates | `test_dedupe.py` | A repeated id whose rows disagree keeps **both** and flags them — the pipeline does not guess |
| Missing values | `test_normalise.py` | Blank refund ≠ 0; blank CSAT is NaN not 0 (policy §8) |
| Unknown reason code | `test_normalise.py` | Labelled UNKNOWN, flagged, **row kept** — tested with a synthetic fixture, never by editing source data |
| Joins | `test_joins_agents.py` | Ambiguous fallback attaches nothing; a test asserts the refund total is **byte-identical before and after joining** |
| Roster | `test_joins_agents.py` | Date-ranged resolution; row count asserted so overlapping assignments cannot fan out and inflate an agent total |
| Refund + replacement | `test_policy.py` | Both detectors; a plain replacement mention does **not** false-positive |
| Open tickets | `test_policy.py` | Included and flagged, never dropped |
| Aggregation | `test_aggregate.py` | Identities hold; a month with no refunds is not invented |
| Impact model | `test_validation_impact.py` | No double counting; conservative bucket arithmetic |
| **The core invariant** | `test_validation_impact.py` | **The AI layer cannot change a refund total** |

### A test that found a real bug
`test_roster_picks_the_assignment_in_force_on_the_ticket_date` failed on first
run. The original `attach_agents` had a fast path for single-row rosters that
skipped date validation entirely and reported `in_force` for a ticket outside
every assignment window. Rewritten as a properly date-ranged vectorised join.
Today's data has one row per agent so nothing was wrong in the output — but the
next export with a transfer in it would have been.

## Layer 4 — AI evaluation

*"Do not claim AI accuracy without measurement."*

### Evaluation set
168 refund tickets, each read individually against `prompts/reason_classifier.md`
and labelled with a reason code, theme, confidence and a verbatim evidence quote.
Stored at `data/eval/gold_labels.csv`.

### Tier 1 (the rules engine) — measured

| Metric | Value |
|---|---|
| Gold set size | 168 |
| Resolved by tier 1 | 159 (94.6%) |
| Escalated to tier 2 | 9 (5.4%) |
| **Accuracy on what tier 1 resolves** | **97.5%** (155/159) |
| Errors | 4 |

Locked by `test_rules_tier_accuracy_against_the_gold_set`, which fails the build
if a pattern edit drops accuracy below 95%.

### The four errors, named

| Ticket | Gold | Predicted | Why |
|---|---|---|---|
| TK-240242 | WTY-BUYBACK | RETURN-QC-OK | Note mentions a reverse pickup for a unit that was faulty; both readings are arguable |
| TK-241067 | RETURN-QC-OK | DOA-REPL | Wrong item shipped, note says *"new unit shipped under doa"* — the agent used DOA language for a fulfilment error |
| TK-241575 | GW-OTHER | RETURN-QC-OK | Genuine goodwill inside a returns context |
| TK-241675 | GW-OTHER | WTY-BUYBACK | Genuine goodwill after a resolved connectivity fault |

**The failure mode has a shape.** Three of four are the boundary between
*genuine goodwill* and *the underlying problem that preceded it*. That is a hard
call for a human too. It is also where a wrong answer matters least: both labels
agree the ticket is not ordinary, and the rupee total is unaffected either way.

### Independent control
Agreement with the **recorded** reason code on the 1,349 refunds that are *not*
GW-OTHER: **90.4%** (1,219 of 1,349).

This is the check that stops the headline being an artefact. A classifier that
simply relabelled everything would disagree with the agent everywhere. This one
agrees nine times in ten where the agent chose a specific code, and disagrees on
**96%** of the tickets where the agent left the dropdown default. That asymmetry
*is* the finding.

### Tier 2 — deliberately unmeasured, and why

The tier-2 labels and the gold labels were produced by the **same model**
(Claude Opus 5, this build session — see `docs/ai-design.md` §6). Measuring tier 2
against them would be measuring a model against itself and reporting the
agreement as accuracy. **So no accuracy figure is claimed for tier 2.**

Tier 2 covers 125 of 2,340 refunds (5.3%), ₹4.1 lakh of ₹67.1 lakh (6.1%).

**Recommended fix, costed:** Vireo hand-labels 50 escalated tickets — about one
hour for one person who knows the SOPs. That closes the last measurement gap in
the system.
